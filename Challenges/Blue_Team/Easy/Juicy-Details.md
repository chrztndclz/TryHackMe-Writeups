**Question 1: What tools did the attacker use? (Order by the occurrence in the log)**


To identify the tools used by the attacker, we examine the **User-Agent** field in the `access.log`. Many security tools send a distinctive User-Agent string by default, allowing us to determine which application generated each request.

#### 1. Nmap

The first tool observed is **Nmap**.

```

```

The **User-Agent** contains `Nmap Scripting Engine`, indicating that the request was generated by Nmap's NSE. The attacker requests `/.git/HEAD`, suggesting they are performing reconnaissance by checking whether the Git repository is publicly accessible, which could expose sensitive source code or configuration files.


#### 2. Hydra

The next tool identified is **Hydra**.

```
::ffff:192.168.10.5 - - [11/Apr/2021:09:16:27 +0000] "GET /rest/user/login HTTP/1.0" 500 - "-" "Mozilla/5.0 (Hydra)"
```

The **User-Agent** explicitly contains `**Hydra**`, confirming the tool used. Hydra is commonly used to perform brute-force or dictionary attacks against authentication services. Since the request targets `/rest/user/login`, it indicates the attacker was likely attempting to discover valid login credentials.




#### 3. sqlmap

The third tool is **sqlmap**.

```
::ffff:192.168.10.5 - - [11/Apr/2021:09:29:14 +0000] "GET /rest/products/search?q=1 HTTP/1.1" 200 - "-" "sqlmap/1.5.2#stable (http://sqlmap.org)"
```

The **User-Agent** contains `**sqlmap/1.5.2**`, identifying the tool as sqlmap. Sqlmap is an automated SQL injection tool used to detect and exploit SQL injection vulnerabilities. The request to the search parameter (`q=1`) is consistent with sqlmap beginning its automated testing of the application's input fields.


#### 4. curl

The fourth tool observed is **curl**.

```

The **User-Agent** identifies `**curl/7.74.0**`. Unlike sqlmap, which automates SQL injection testing, curl allows an attacker to manually send custom HTTP requests. #### 5. Feroxbuster

The **User-Agent** contains `**feroxbuster/2.2.1**`, confirming the use of Feroxbuster. Feroxbuster is a directory and file enumeration tool used to discover hidden resources on a web server. The request to a seemingly random path suggests the attacker is performing content discovery to locate hidden endpoints, files, or directories that may provide additional attack opportunities.

**Question 2: What endpoint was vulnerable to a brute-force attack?**


To determine which endpoint was targeted by a brute-force attack, we examine the `access.log` for requests generated by password-cracking tool

```
::ffff:192.168.10.5 - - [11/Apr/2021:09:16:27 +0000] "GET /rest/user/login HTTP/1.0" 500 - "-" "Mozilla/5.0 (Hydra)"
```

The **User-Agent** field contains `Hydra`, identifying the tool as **Hydra**, a well-known password-cracking utility used to perform brute-force and dictionary attacks against authentication services.

The request targets the endpoint `**/rest/user/login**`, which is the application's login API. Since login endpoints require a username and password for authentication, they are common targets for brute-force attacks. The presence of Hydra making requests to this endpoint strongly suggests that the attacker was attempting to repeatedly test different username and password combinations in an effort to obtain valid credentials.

> Answer: /rest/user/login


**Question 3: What endpoint was vulnerable to SQL injection?**

To identify the endpoint vulnerable to SQL injection, we examine the `access.log` for requests generated by SQL injection tools or containing SQL injection payloads.

```
::ffff:192.168.10.5 - - [11/Apr/2021:09:29:14 +0000] "GET /rest/products/search?q=1 HTTP/1.1" 200 - "-" "sqlmap/1.5.2#stable (http://sqlmap.org)"

```

The **User-Agent** field contains `**sqlmap/1.5.2**`, indicating that the request was generated by **sqlmap**, a tool specifically designed to detect and exploit SQL injection vulnerabilities.

The request targets the `**/rest/products/search**` endpoint, with the query parameter `q=1`. Sqlmap commonly begins by sending simple requests to an input parameter before injecting various SQL payloads to determine whether the application is vulnerable. Since sqlmap is interacting with the `q` parameter of the search endpoint, it suggests that the attacker identified this parameter as a potential injection point and was testing it for SQL injection vulnerabilities.

This is further supported by subsequent log entries, where the attacker uses **curl** to send a manually crafted **UNION SELECT** SQL injection payload against the same endpoint, attempting to retrieve sensitive data such as user IDs, email addresses, and passwords from the database. This confirms that `/rest/products/search` was the endpoint targeted for SQL injection.

> Answer: /rest/products/search


**Question 4: What parameter was used for the SQL injection?**

To identify the parameter targeted for SQL injection, we examine the request made by **sqlmap** to determine which input field it is testing.

```
::ffff:192.168.10.5 - - [11/Apr/2021:09:29:14 +0000] "GET /rest/products/search?q=1 HTTP/1.1" 200 - "-" "sqlmap/1.5.2#stable (http://sqlmap.org)"
```

```
q=1
```

The request is sent to the endpoint `**/rest/products/search**`, where the query string contains the parameter `**q=1**`. In an HTTP GET request, the value after the `?` represents the query parameters being passed to the application. Here, `q` is the parameter name, while `1` is the value supplied to it.

Since **sqlmap** is testing this request for SQL injection, it indicates that the attacker identified the `q` parameter as a potential injection point. This is further confirmed by subsequent log entries where the attacker replaces the value of `q` with a malicious **UNION SELECT** SQL injection payload to extract data from the database, demonstrating that this parameter was the target of the attack.

> Answer: q

**Question 3: What user information was the attacker able to retrieve from the endpoint vulnerable to SQL injection?**

To determine what information the attacker retrieved, we examine the SQL injection payloads sent to the vulnerable `/rest/products/search` endpoint.

```
::ffff:192.168.10.5 - - [11/Apr/2021:09:29:58 +0000] "GET /rest/products/search?q=%27))%20UNION%20SELECT%20%271%27,%20%272%27,%20%273%27,%20%274%27,%20%275%27,%20%276%27,%20%277%27,%20%278%27,%20%279%27%20FROM%20Users-- HTTP/1.1" 200 - "-" "Mozilla/5.0 (X11; Linux x86_64; rv:78.0) Gecko/20100101 Firefox/78.0"
```


The SQL injection payload contains the statement:
```
UNION SELECT id, email, password, '4', '5', '6', '7', '8', '9' FROM Users--
```

This shows that the attacker is querying the `**Users**` table and specifically requesting the `id`, `email`, and `**password**` columns. Earlier requests containing `ORDER BY` and placeholder values (`'1'`, `'2'`, `'3'`, etc.) were used to determine the correct number of columns required for a successful **UNION SELECT** attack. Once the attacker confirmed the query structure, they replaced the placeholder values with actual database column names.

Although the payload requests the `id`, `email`, and `password` fields, the question asks specifically for the **user information** that was retrieved. The **email** and **password** fields contain user account information, whereas **id** is simply a database identifier. Therefore, the user information extracted through the SQL injection was the users' **email addresses** and **passwords**.

**Answer:** `Email, Password`

**Question 5: What service and account name were used to retrieve files from the previous question? (service, username)**

To determine which service and account were used to retrieve the files, we examine the `**vsftpd.log**`, which records authentication attempts to the FTP server.

```

The second log entry shows a successful login:

- `[ftp]` identifies the service handling the connection, confirming that the attacker connected through the **FTP** service.
- The text `anon password "IEUser@"` indicates that the attacker logged in using the **anonymous FTP account**. In FTP, anonymous logins typically use the username `anonymous`, while any password (commonly an email address such as `IEUser@`) is accepted.

This correlates with the earlier evidence where the attacker attempted to access files under the `**/ftp**` endpoint, indicating that the files were being accessed through the FTP service using an anonymous account.

**Question 6: What service and username were used to gain shell access to the server? (service, username)**

```
Apr 11 09:38:29 thunt sshd[8162]: Failed password for www-data from 192.168.10.5 port 40066 ssh2
```

This log entry was generated by `sshd`, the Secure Shell (SSH) daemon, indicating that the attacker was attempting to authenticate to the server using the **SSH** service.

The message `Failed password for www-data` identifies the username used during the login attempt. Although the password authentication failed, the log clearly shows that the attacker targeted the `www-data` account in an attempt to gain interactive shell access to the server through SSH.

The `www-data` account is commonly used by web server processes on Linux systems. Attackers often target this account because compromising a web application may provide access to it, making it a logical account to attempt when trying to establish a shell.

>Answer: ssh, www-data
